# exchange-core Zig port

This directory contains the completed Java -> Zig production port for
`src/main/java/exchange/core2/core` as verified on 2026-07-31.

## Parity status

The observable Java production responsibilities are closed for the scoped
package. `JAVA_PRODUCTION_CLASS_MAP.md` maps all 91 Java production files to
their Zig owners, `MIGRATION_COVERAGE.md` is the evidence ledger, and
`PROCESSOR_PARITY_DECOMPOSITION.md` records the processor timing and ownership
model. JVM mechanisms that cannot cross a native boundary—object identity,
thread factories, reflection, and `Unsafe`—have explicit typed capability or
native-runtime boundaries rather than silent substitutes.

The persistent per-shard grouped worker core is now the production default for
`ExchangeApiSharded` and Java-default orchestration. It has stable stage
frontiers, journal-gated results before delayed R2, one paired R1/R2 worker per
RE, one worker per ME, Java-compatible same-group R1 lookahead, cross-group R2
barriers, global-command barriers, callback-safe publication, and
query/snapshot/reset/persistence/shutdown quiescence. If matching fails at
sequence F, same-group R1 tail mutations may already exist just as they can in
Java; the runtime is then poisoned permanently and neither F nor its suffix can
publish matching results. Explicit `immediate` mode remains available as a
compatibility pin. Default 1x1 orchestration therefore uses sharded/XCM2; when
its newest committed snapshot is legacy XCM1, grouped startup fails with
`LegacyXcm1RequiresImmediateOrMigration` instead of silently starting empty.
Pin `immediate` to restore that state, or migrate it to XCM2.

The current orchestrator A/B produced the same canonical
`115306a07a302c98` final-state fingerprint in all 16 counterbalanced rows. Its
executable ReleaseFast capacity floors passed for every persistent 1x1 and 4x2
row. Persistent medians were 523096.04 settled and 785795.70 detached
commands/s for 1x1, and 171107.15 settled and 232996.80 detached commands/s for
4x2. This is a same-host native capacity gate, not a cross-host Java throughput
claim. See `ORCHESTRATOR_AB_BENCHMARK_REPORT_2026-07-31.md`.

Current closure evidence is 21/21 focused persistent-pipeline tests in Debug
and ReleaseSafe, 43/43 through the sharded API in ReleaseSafe, and 67/67
grouped tests through the orchestrator in ReleaseSafe. The full serialized
repository gate passed 26/26 steps and 2255/2255 tests: 1117 Debug, 1117
ReleaseSafe, and 21 evidence-tool tests, with the exact 96/96 default fixture
manifest, API surface, Java API parity audit, and the 91-class production map
check. Temurin 11.0.32+9 ran the complete Java suite (174 tests, 0
failures/errors, 10 intentionally skipped fixture writers) and
the opt-in persistence writer in two separate JVM processes. The latter
regenerated byte-identical Chronicle `.ecs`/`.ecj` artifacts, recovered
snapshot and journal state in Java, and excluded process-local identity hashes
from the portable manifest. The committed fixture then restored/replayed in
Zig in both Debug and ReleaseSafe.

## Standalone TCP demo

`zig build` installs `exchange-core-server` and `exchange-core-client` in
`zig-out/bin`. Start the server with `zig build run-server`, then send commands
from another terminal with `zig build run-client -- ping`. The programs use a
local newline-delimited demo protocol—not FIX or REST—and default to
`127.0.0.1:7379` with symbol `241` (base `11`, quote `15`).

See `src/zig/USAGE_EXAMPLES.md` for the complete two-terminal transaction
quickstart, command reference, graceful shutdown, embedded integration,
persistence, orchestrator, and migration workflow examples.

## Migration rules

- Keep behavioral parity with Java first, then optimize.
- Preserve code mappings (enum/integer values) for wire compatibility.
- Add parity tests for every ported module before integrating it.
- Use explicit Zig error sets for decode/validation failures.
- Use exhaustive `switch` statements for command/event handling.
- Apply Tiger Style discipline for:
  - aggressive invariant checking (`std.debug.assert`) at module boundaries,
  - explicit control flow and no hidden side effects,
  - predictable memory ownership (`init`/`deinit`, no global allocators),
  - small, testable functions with bounded loops,
  - deterministic seeded perturbation simulations for async callback/poll parity and exactly-once delivery behavior,
  - deterministic one-shot helper simulations that cross-check `processCommandResultCode`/`processCommandFullResponse` against explicit async submit+drain+take flows with per-step detailed state-hash convergence.
